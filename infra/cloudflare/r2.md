# Cloudflare R2: buckets, domain, tokens

Nothing here is applied automatically. Every owner step is marked **[You]**. R2 may ask for a payment method on the Cloudflare account (the free allowance still applies); Workers Paid is bought in the same sitting. The lead may create the buckets and the domain through the Cloudflare API instead; the settings below are what must end up true.

## Buckets

| Bucket | Access | Used by | Notes |
|---|---|---|---|
| `azira-images` | **public through `https://img.azira.com.au` only** | Medusa file uploads (S3 file provider); the storefront image loader | Product, category and banner images. `r2.dev` access stays disabled. |
| `azira-next-cache` | private | the storefront Worker (OpenNext incremental cache) | Bound in `apps/storefront/wrangler.jsonc`; no API token. Holds rendered pages, never customer data. |
| `azira-db-backups` | private | the backup job (`infra/backup/backup.sh`) | 35-day lifecycle rule; bucket-scoped token. |

## Create the buckets [You]

Cloudflare dashboard → **R2 object storage → Create bucket**. For each of the three names above: name as written, **Location: Oceania (OC)** (the closest hint to Sydney; it cannot be changed later), Default storage class **Standard**, **Create bucket**.

(Alternative, from the PC after `npx wrangler login`: `npx wrangler r2 bucket create <name>` for each name.)

## Public images on `img.azira.com.au` [You]

1. **R2 object storage → `azira-images` → Settings → Custom Domains → Add → `img.azira.com.au` → Continue → Connect Domain.** The status goes from Initializing to Active within a few minutes (use *Retry connection* in the bucket's `...` menu if it stalls). The domain must be a zone in this same account. R2 creates the DNS record itself.
2. **Settings → Public Development URL → Disable** (type `disallow`). Only the custom domain may serve the bucket, so WAF rules and the cache rule apply to every request.
3. The cache rule and Image Transformations for `img.azira.com.au` are in `rules.md`, section 5.
4. No bucket CORS is needed: the browser loads images with plain `<img>` tags and uploads go through the backend.

Test after the first admin upload: `curl -sI https://img.azira.com.au/<file name>` returns `200` with `cf-cache-status`, and `https://img.azira.com.au/cdn-cgi/image/width=640,quality=75,format=auto/<file name>` returns a smaller image.

## Backups bucket rules [You]

1. **R2 → `azira-db-backups` → Settings → Object Lifecycle Rules → Add rule.** Name `expire-after-35-days`, prefix empty (whole bucket), action **delete uploaded objects after 35 days**, **Save changes**. Objects are removed within about 24 hours after they expire. (The default rule that aborts unfinished multipart uploads after 7 days is already there; leave it.)
2. **Recommended, optional: Settings → Bucket lock rules → Add rule.** Name `keep-35-days`, prefix empty, retention **35 days**. Nobody, including a stolen backup token, can then overwrite or delete a backup for 35 days (a blocked request gets HTTP 409). The price: a test backup cannot be deleted either, and the bucket cannot be emptied while the rule exists. `backup.sh` copes with it: it uploads `<key>.partial`, copies it to the final key and then tries to delete the `.partial`; under the lock that delete is refused, which the script logs and ignores, so each run leaves one extra `.partial` copy until the lifecycle rule removes it (twice the storage of the backups; restores skip `.partial`). Locks take precedence over the lifecycle rule, and the two periods match, so nothing is kept longer than 35 days. Decide before the first backup.
3. Mention the 35-day backup retention in the privacy policy.

## API tokens [You]

R2 object tokens use the S3 API. **R2 object storage → Overview → Account Details → API Tokens → Manage → Create Account API token** (the button name may read "Create API token"). One token per consumer:

| Token name | Permissions | Buckets (Specify bucket) | Used by | Goes into |
|---|---|---|---|---|
| `azira-files-rw` | Object Read & Write | `azira-images` | Medusa | GitHub secrets `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` (already set) |
| `azira-backups-rw` | Object Read & Write | `azira-db-backups` only | the backup job | `/opt/azira/backup.env` (see docs/hosting.md, Backups) |

- **TTL:** forever, with a yearly rotation reminder in your calendar.
- **Client IP Address Filtering:** if the form offers it, **Include** the droplet's IPv4 and IPv6. A leaked token is then useless elsewhere. Update it whenever the droplet is rebuilt. (Leave it off for the file token if you also upload from your own PC.)
- After **Create API Token**, copy the **Access Key ID**, **Secret Access Key** and the jurisdiction endpoint `https://<account id>.r2.cloudflarestorage.com` straight into your password manager. The secret is shown once.
- "Object Read & Write" is the narrowest permission R2 offers for uploads (there is no write-only token), so a stolen backups token could read the encrypted backups; they are age-encrypted, and the bucket lock above stops deletion.
- **Rotation:** create the new token, update the GitHub secret and run the "Backend deploy" workflow again (for files; the next timer run for backups), check an upload, then delete the old token.
- Restoring from a PC (monthly drill) needs read access: use a short-lived `Object Read only` token for `azira-db-backups`, or the dashboard download, and delete it afterwards.

## Backend settings for file storage

The deploy workflow writes these into `/opt/azira/.env` from GitHub secrets (names read by `apps/backend/src/lib/file-storage.ts`):

```
FILE_PROVIDER=s3
R2_ENDPOINT=https://7b7865326875e0dea1285c31309d77a4.r2.cloudflarestorage.com
R2_BUCKET=azira-images
R2_ACCESS_KEY_ID=<from azira-files-rw>        (GitHub secret)
R2_SECRET_ACCESS_KEY=<from azira-files-rw>    (GitHub secret)
FILE_URL=https://img.azira.com.au
# R2_REGION is optional and defaults to "auto", which R2 requires.
```

The provider is configured with `region: "auto"` and `acl: false` (R2 has no object ACLs). A missing variable stops the server at start and names the variable. Local development keeps the local file provider (leave `FILE_PROVIDER` unset).

**Check after the first deploy:**
1. Upload one product photo in the admin. It should appear in `azira-images` and display in the admin, with a URL on `https://img.azira.com.au/...`.
2. If the upload fails with an error about the bucket name in the host name, a DNS or TLS error, or `NoSuchBucket`, the client is using virtual-hosted addressing. R2 should accept both styles, so this is unlikely. The fix is a one-line change in `apps/backend/src/lib/file-storage.ts`: add `additional_client_config: { forcePathStyle: true }` to the provider options, then redeploy.
3. If the upload works but the image URL does not load, check that the custom domain is **Active**, that the object name in the URL matches, and that `FILE_URL` has no trailing slash.
